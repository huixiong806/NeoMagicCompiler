# 开发流程（照着做就能跑起来）

> 目标读者：第一次接触这个仓库的人（或 AI）。
> 命令都从 `Makefile` 与 `README.md` 抄来并核对过；有坑的地方单独标出来。
> 架构说明见 [`架构.md`](架构.md)，写关卡见 [`关卡编写规范.md`](关卡编写规范.md)。

---

## 1. 环境要求

| 依赖 | 版本 | 用途 / 备注 |
|------|------|------------|
| Rust | **1.75+**（本项目在 cargo/rustc 1.94 上开发） | 全部引擎与桌面壳；edition 2021，workspace `resolver = "3"` |
| Node.js | **≥ 18**（本项目在 node 24 上开发） | 编辑器前端（Vite + TypeScript）与 Tauri CLI |
| mdBook | **≥ 0.4**（本项目在 0.5.3 上开发） | `cargo install mdbook`；把 `compiler-content/` 构建成 `app/src/` 下的 HTML |
| GNU make | 任意 | `Makefile` 的入口；Windows 上用 Git Bash / MSYS2 / WSL，或用 `make` 的移植版 |

还需要：**WebView2 运行时**（Windows 上 Tauri 2 的前置条件，Win10/11 一般已自带）。
打包安装包另外需要平台工具链（Windows 上是 MSVC）。

根目录的 `.cargo/config.toml` 设了 `[net] offline = true`：**依赖必须已经在本地缓存里**，
构建不会去访问 crates.io。`cargo` 只尝试一次"更新索引"就会在全球包缓存上持锁等待网络超时，
多进程同时构建时其余进程全部排在它后面，表现得像死锁（一堆 cargo 进程、零个 rustc）——
这个坑踩过一次，所以显式关掉了网络。

## 2. 第一次跑起来

```bash
# 1) 先确认三个工具都在（缺哪个会直接报出来）
make smoke

# 2) 装 npm 依赖（app/ 与 compiler-content/frontend/ 两个 package）
make setup

# 3) 起桌面版（会先构建书 + 前端，再启动 Tauri）
make dev
```

`make dev` 的实际展开（`Makefile`）：

```make
dev: book-build setup
	cd app && npm run tauri dev
```

`book-build` 会先跑 `theme-build`（`cd compiler-content/frontend && npx.cmd vite build`，
产物落在 `compiler-content/theme/dist/`），再跑 `cd compiler-content && mdbook build`，
HTML 落在 `app/src/`。Tauri 的 `frontendDist` 指向 `../src`，所以桌面版加载的就是这份本地 HTML。

> ⚠ **没有前端热更新**：改了 `.ts` 或关卡 `.md` 之后，要么重跑 `make book-build`，
> 要么直接重跑 `make dev`。`app/src/` 是**生成物**，`.gitignore` 挡住了它
> （`app/src/*`，只留 `.gitkeep`），**不要手改**。

只想在浏览器里看教学内容（不玩、不能运行代码）：

```bash
make book-serve     # 起 mdbook serve，默认 http://localhost:3000
```

浏览器预览下编辑器能写代码，但「运行 / 调试 / 提交」需要 Rust 后端，前端会明确提示
"这是浏览器预览模式，还没有连上魔导核心"，不会静默失败。

## 3. 构建与测试

### 3.1 常用命令（全部来自 `Makefile`）

| 命令 | 做什么 |
|------|--------|
| `make smoke` | 开工前的环境自检：打印 `cargo` / `node` / `mdbook` 的版本，缺哪个就直接报出来 |
| `make help` | 列出所有目标（`.DEFAULT_GOAL`） |
| `make setup` | `npm install`（`app/` + `compiler-content/frontend/`） |
| `make theme-build` | 只构建前端 bundle：`cd compiler-content/frontend && npx.cmd vite build` |
| `make theme-check` | 只做 TypeScript 类型检查：`npx.cmd tsc --noEmit` |
| `make book-build` | `theme-build` + `mdbook build`（产物在 `app/src/`） |
| `make book-serve` | `mdbook serve --open`（浏览器预览，热更新） |
| `make book-test` | `book-build` + **关卡自检** + **关卡文件一致性检查**（内容守门人） |
| `make check` | `cargo check --workspace` |
| `make test-sim` | `cargo test -p riscv-simulator`（最快的反馈回路） |
| `make test` | `book-test` + `cargo test --workspace`（提交前跑这个） |
| `make dev` | `book-build` + `setup` + `npm run tauri dev` |
| `make release` | `book-build` + `setup` + `npm run tauri build`（生成安装包） |
| `make clean` | `cargo clean` + 删掉 `app/src/` 下 mdBook 生成的各种 HTML/JS/CSS |

> ⚠ **Windows 上 `Makefile` 写的是 `npm.cmd` / `npx.cmd`**，这不是笔误：`make` 会用 PATH 里的
> sh/bash（本机是 MSYS2 的 sh）跑每条命令，而 Windows 的 Node 只提供 `npx.cmd` / `npm.cmd`，
> POSIX shell **不会**自动补 `.cmd`，于是 `npx vite build` 会报
> `/bin/bash: C:/Program Files/nodejs/npx: No such file or directory` —— 看起来像"Node 没装"。
> 手工敲命令时两种写法都可以（`npx` 在 cmd/PowerShell 里能用）；**改 Makefile 时别改掉 `.cmd`**。

### 3.2 分层的测试命令

```powershell
# 全部（引擎 + 领域层 + IPC + 两门内容检查）
cargo test --workspace

# 单个 crate（改哪就测哪，快）
cargo test -p riscv-simulator
cargo test -p riscv-assembler
cargo test -p starlang
cargo test -p neomagic-core
cargo test -p neomagiccompiler        # 桌面壳：10 条 IPC 链路集成测试，不需要 GUI

# 前端
cd compiler-content\frontend; npx tsc --noEmit
cd compiler-content\frontend; npx vite build
```

`cargo test -p neomagiccompiler` 能覆盖整条 IPC 链路，是因为业务逻辑在 `api.rs` 里、
不依赖 Tauri（见 [`架构.md`](架构.md) §2）。**这是本项目最值得保持的一条纪律。**

### 3.3 关卡自检（内容的质量底线）

```powershell
# 全部关卡：用每关的参考解跑该关全部测例
cargo test -p neomagic-core selfcheck -- --nocapture

# 只查自己那几关（并行写关卡时用）
$env:NMC_SELFCHECK="3-4,3-5,3-6"; cargo test -p neomagic-core selfcheck_only -- --nocapture

# 逐条测例打印"输入 / 期望 / 实际"（调试单关时用，比看汇总省时间）
$env:NMC_SELFCHECK="4-4"; $env:NMC_SELFCHECK_VERBOSE="1"; cargo test -p neomagic-core selfcheck_verbose -- --nocapture
```

bash 下把 `$env:X="..."` 换成 `X=... `（前置环境变量）。

含义：自检通过 → 这一关**至少有解**、测例与参考解自洽；自检失败 → 测例或参考解写错了。
默认的汇总**只报第一条失败测例**，所以修一关的时候请用 `NMC_SELFCHECK_VERBOSE`（见
[`架构.md`](架构.md) §6.1）。

### 3.4 两门检查分别抓什么

| 命令 | 抓什么 | 抓不住什么 |
|------|--------|-----------|
| `cargo test -p neomagic-core selfcheck` | 参考解能不能过测例（关卡可解性、测例/参考解自洽） | **编辑器约束**、叙事内容、前端按钮行为 |
| `cargo test -p neomagic-core every_level_page_and_test_config_are_consistent` | `language` 一致、有初始代码、`level` 与文件名一致、约束行号在范围内 | 行号合法但语义写错（提示指错行）、锁住了不该锁的行 |

**"自动测试全绿"≠"关卡可玩"** —— 试玩阶段必须一关一关点过去（这也是为什么 `make dev` 不能省）。

### 3.5 `mdbook test` 为什么不用

它只会把**没标语言**的代码块当 **Rust** 编译。关卡页里的块是星之语汇编、token 序列、伪代码，
于是几十处都会报 `cannot find value` / `undeclared type`——那些报错没有意义。
`make book-test` 已经换成"自检 + 文件一致性检查"，详见 `Makefile` 里的注释与
[`架构.md`](架构.md) §8。

## 4. 写一个新关卡

完整格式见 [`关卡编写规范.md`](关卡编写规范.md)，这里是**动作清单**。

### 4.1 建三个文件

| 文件 | 注意 |
|------|------|
| `compiler-content/src/cN_M.md` | 叙事 + 一个 ```` ```riscv ```` 块；块里先 JSON 配置、单独一行 `---`、再初始代码 |
| `compiler-content/src/tests/cN_M.json` | 测例与判定配置；`level` 必须与文件名一致 |
| `compiler-content/solutions/cN_M.s`（汇编）或 `.c`（星咒） | **参考解**；扩展名由 `language` 决定，缺了就报"没有参考解" |

命名：`N` 章号、`M` 关号，**不补零**（`c3_4.md`，不是 `c3_04.md`）。
三处 `level` 字段（关卡页 JSON、测例 JSON、关卡 ID）必须一致。
`compiler-content/src/SUMMARY.md` 里加一行目录项，否则这页不会出现在书里。

### 4.2 验证（必须全过）

```powershell
# 1) 只查自己这几关
$env:NMC_SELFCHECK="3-4"; cargo test -p neomagic-core selfcheck_only -- --nocapture

# 2) 关卡文件一致性 + 编辑器约束行号
cargo test -p neomagic-core every_level_page_and_test_config_are_consistent

# 3) 提交前跑全量
make test
```

第 2 条**不能跳过**：编辑器约束写错时自检照样全绿（自检不经过编辑器），
真实事故里有一关因为 `readonlyPrefix` 大于代码行数导致**整篇被锁死、玩家一个字都改不了**。

### 4.3 关卡作者最容易踩的几个坑

只列最容易反复出现的，其余在 [`关卡编写规范.md`](关卡编写规范.md)：

1. **`a7` 是 `x17`，不是 `x11`**（`x11` 是 `a1`）。把调用号写错地方的后果是
   "每一个 `ecall` 都被当成结束程序"，现象是"跑得飞快、输出全空"。
2. **跨 `jal` 要保住的值只能放 `s0`–`s11`**；`t0`–`t6` / `a0`–`a7` 会被你自己写的辅助函数静默冲掉。
3. **`.word` 不会自动对齐**：`.asciz` 后面接 `.word` 要显式 `.align 4`，否则 `lw` 报未对齐访问。
4. **"空输入/空输出"的测例必须额外检查内存**：输出比对会丢掉空行，一个什么都没实现的骨架也能通过。
5. **遇到"某个指令行为诡异"的结论，先用最小程序实测**。本项目有两条吓人的"引擎 bug"断言
   （`lw` 读端口吞字节、`getc` 破坏 `t0`）都被实测推翻，真凶都是关卡作者自己程序里的辅助函数。

## 5. 编码纪律（Windows 上的血泪）

### 5.1 只用 UTF-8 写文件

**绝对不要**用 PowerShell 的 `Set-Content` / `Out-File` / `Get-Content | Set-Content` 写含中文的源码或文档
—— 它们会按 GBK 解释导致乱码，**不可逆**。本项目因此毁过一个 `lib.rs` 和一批 `solutions/*.s`。

- 改文件用**编辑工具**（写工具 / 编辑工具），或明确按 UTF-8 写入的方式；
- 判断编码要看**读取工具**或按 UTF-8 解码的结果；
- ⚠ PowerShell 控制台**显示**中文乱码（GBK 解码）**不代表文件坏了** —— 曾经据此误判过一批好文件；
- 数行数不要信 `Get-Content`（这台机器上它会把行合并），要用读取工具或 `git show`。

### 5.2 提交信息怎么写（唯一不踩坑的写法）

在命令行里内联多行中文、或用 PowerShell here-string（`<<'EOF'` 在 pwsh 里根本不合法）都会出问题。
正确做法是：**用写工具把提交信息写进一个临时 UTF-8 文件，再让 git 读它**。

```powershell
# 1) 用编辑工具写 C:\Users\<你>\AppData\Local\Temp\nmc-msg.txt（UTF-8，内容形如）：
#    第四章补齐：4-7~4-12 全部通过自检
#
#    - 修掉 ble/bleu 操作数写反（编成 bge/bgeu）
#    - 新增编辑器约束行号检查
# 2) 再提交：
git add -A
git -c i18n.commitEncoding=UTF-8 commit -F "C:\Users\<你>\AppData\Local\Temp\nmc-msg.txt"
```

`-c i18n.commitEncoding=UTF-8` 是在告诉 git "这个文件是按 UTF-8 写的"，
这样 `git log` 才不会把中文显示成乱码。**提交信息文件放系统临时目录，别放进仓库。**

### 5.3 提交前必须做的事

```powershell
git status --short      # 看一眼有没有混进不该提交的东西
```

**每次提交前都要看**。历史上被误提交过两次子代理留下的调试残件
（探针关卡 `c0_0.md`/`c9_9.md`、`ztmp_probe/`、独立的 `CARGO_TARGET_DIR` 残留 269 MB）。
`.gitignore` 挡住了一部分（`compiler-content/src/c0_0.md` 等、`ztmp_probe/`、`crates/*/tests/`），
但挡不住全部。

另外两条与构建有关的：

- **不要**另建 `CARGO_TARGET_DIR`：多个 cargo 同时构建会抢 `target/` 锁
  （`Blocking waiting for file lock`）。真需要就等 30 秒重试，或者**事后一定删掉**那个目录。
  仓库里 `crates/*/tests/` 是被 `.gitignore` 忽略的：本项目所有测试都写在
  `#[cfg(test)] mod tests` 里，**任何人**在那里放一个编译不过的文件，整个 workspace 的
  `cargo test` 都会挂。
- 测试断言别直接比长字符串（会打出几 MB 日志），先比长度或取前缀。

## 6. 分支与提交流程

- **主分支 `master` 不要动。** 所有开发都在 `feat/complete-game`（当前分支）上进行，完成后由主负责人合并。
- 远端是 Gitee：`orangebird/neo-magic-compiler`。
- 提交粒度：一个可验证的改动一个提交（"补完第四章 4-7~4-12"、"修 `ble` 操作数"），
  提交信息写清**为什么**（尤其是修 bug 时：现象 → 根因 → 修法）。
- 提交前跑 `make test`；只改文档时至少跑 `mdbook build` 确认没搞坏书。
- 推送前确认 `git status --short` 干净，且没有探针文件/临时目录。

## 7. 常见问题速查

| 现象 | 原因 / 处置 |
|------|------------|
| 改了关卡但游戏里还是旧内容 | `app/src/` 是构建产物，需要重跑 `make book-build`（或 `make dev`）。桌面版加载的是这份 HTML，Rust 侧只提供关卡数据 |
| 改了关卡数据但引擎读到旧的 | `embedded-content` 让内容在**编译期**嵌入；开发时优先读磁盘（`prefer_repo_or_embedded`），但如果磁盘上没有 `compiler-content/src` 就会用嵌入内容 |
| "进度没记住" | 看启动日志的 `[存档] <路径>` 那一行（见 [`存档格式.md`](存档格式.md)） |
| 点「倒退」没反应 | 调试会话必须打开 `record_history`（`Runner::debug_simulator` 会开）；如果是在别处造的 `Simulator`，`step_back` 会静默无效 |
| 一堆 cargo 进程卡住、零个 rustc | 离线构建没生效 / 有人设了别的 `CARGO_TARGET_DIR` 在抢锁 |
| 关卡自检全绿但关卡不可玩 | 编辑器约束的问题（自检不经过编辑器）→ 跑 `every_level_page_and_test_config_are_consistent`，再人工试玩 |
| `cargo test` 编译不过，报错在 `crates/*/tests/` | 有人在那儿留了探针文件。那个目录不是本项目放测试的地方，删掉 |
