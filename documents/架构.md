# 架构设计（网页化 + 本地项目桥接）

> 本文定义 `no_story` 分支的**目标系统架构**，并明确标注哪些模块**直接复用现有 Rust 代码**、哪些模块是**网页化改造的新增部分**。
> 原 `Tauri 2 + mdBook` 桌面壳方案已决定废弃，迁移路径见文末 §7。

---

## 1. 总体架构：Web SPA + 双执行后端

为了同时满足**「极佳的网页交互与动画展示」**与**「后期在本地维护完整 C 语言项目」**两个核心诉求，系统采用**统一前端 + 双引擎适配器**架构：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│  表示层  web/  (Vite + TypeScript + React + Tailwind + CodeMirror 6)     │
│   ├─ 关卡地图 (Skill Tree)       ├─ 交互动画教学引擎 (Visualizers)        │
│   ├─ 独立 Playground (在线/本地)  └─ 概念图鉴 Wiki                        │
└───────────────────┬─────────────────────────────────┬───────────────────┘
                    │ 统一 EngineClient 接口           │
       ┌────────────▼────────────┐       ┌────────────▼────────────┐
       │  模式 A：浏览器内置引擎   │       │  模式 B：本地桥接客户端  │
       │  crates/nmc-wasm (WASM) │       │  HTTP + WebSocket       │
       │  零安装运行第 1~2 章     │       │  127.0.0.1:17320        │
       └────────────┬────────────┘       └────────────┬────────────┘
                    │                                 │
                    │                    ┌────────────▼────────────────────┐
                    │                    │  crates/nmc-bridge (本地守护进程) │
                    │                    │   ├─ 识别 nmc.project.json       │
                    │                    │   ├─ notify 文件变动监听         │
                    │                    │   ├─ 调用本机 gcc/clang/make     │
                    │                    │   ├─ 沙箱超时运行玩家编译器       │
                    │                    │   └─ 存档本地同步                │
                    │                    └────────────┬────────────────────┘
                    │                                 │
                    └────────────────┬────────────────┘
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  核心领域与执行层  crates/ （几乎 100% 复用现有 Rust 代码）                │
│   ├─ neomagic-core      关卡加载 / 运行器 / 判定器 / 存档 / 自检          │
│   ├─ starlang           C 子集 → RISC-V 汇编（第 2 章执行与对照）         │
│   ├─ riscv-assembler    两遍扫描汇编器（文本 → 机器码 + 行号映射）         │
│   └─ riscv-simulator    RV32IM 模拟器 + MMIO + 历史回溯（单步/倒退）       │
└─────────────────────────────────────────────────────────────────────────┘
```

**核心架构决策的理由**：

1. **为什么放弃 Tauri + mdBook**：mdBook 本质是静态文档生成器，难以承载丰富的动画组件、双栏联动调试器与路由状态管理；去掉 Tauri 壳后，前端成为标准 Web 应用，既可本地打开也可直接部署静态站点。
2. **为什么引入 `nmc-bridge`**：浏览器受安全沙箱限制，无法直接调用本机 `gcc`/`make` 或执行玩家编译出的原生二进制文件。通过一个极轻量的本地 Rust 桥接进程，玩家既能享受浏览器丝滑的 UI 与动画，又能在自己熟悉的本地 IDE 中自由管理多文件 C 工程。
3. **为什么核心引擎仍全在 Rust 中**：现有的 `riscv-simulator`、`riscv-assembler`、`starlang`、`neomagic-core` 已经过充分单元测试与 53 关自检验证。同一份 Rust 代码既可编进 `nmc-wasm` 给浏览器跑，又可直接被 `nmc-bridge` 原生调用，**算法与判定逻辑零重复**。

| Crate | 当前状态 | 在新架构中的职责 | 需做的最小适配 |

## 3. 新增后端层：`nmc-wasm` 与 `nmc-bridge`

### 3.1 `crates/nmc-wasm`（浏览器内置引擎）

- **目标**：让玩家打开网页即可零安装游玩第 1、2 章和在线沙盒。
- **暴露能力**：通过 `wasm-bindgen` 导出 `run_code`、`submit_code`、`debug_start`、`debug_step`、`debug_step_back`、`debug_continue`、`debug_reset`、`compile_starlang_with_map`。
- **防卡死**：在浏览器中运行于 **Web Worker** 内，避免玩家写出死循环（在触发 `maxInstructions` 上限前）阻塞 UI 动画线程。

### 3.2 `crates/nmc-bridge`（本地 C 项目桥接服务）

一个单文件可执行程序（基于 `axum` + `tokio` + `notify`），默认仅监听 `127.0.0.1:17320`（拒绝非本机访问，保障安全）。

**核心职责**：

1. **项目识别与环境体检**：
   - 读取项目根目录的 `nmc.project.json`；
   - 自动检测本机 C 编译器（`gcc` / `clang` / `make`）版本并回报给网页。
2. **文件监听（Watch Mode）**：
   - 监听 `src/`、`include/`、`Makefile` 等源码目录变化（带 300ms 防抖）；
   - 通过 WebSocket 推送 `project.changed` 事件，前端可配置「保存即自动构建并运行当前关测试」。
3. **构建与安全执行**：
   - 执行项目中配置的构建命令（如 `make` 或 `gcc src/*.c -o build/compiler`），实时流式推送 `stdout`/`stderr` 构建日志；
   - 按关卡测例依次调用玩家编译出的可执行文件，强制施加**超时限制**（默认单测例 2 秒）与**输出体积上限**（防死循环刷屏），捕获退出码与崩溃信号（如段错误 `SIGSEGV`）并翻译为人话提示。
4. **接入核心判定与可视化轨迹**：
   - 拿到玩家程序的输出后，根据关卡类型送入 `BotVM`（第 3 章）或 `riscv-assembler` + `riscv-simulator`（第 4 章）；
   - 生成判定报告，并支持把**任意一条测例（尤其是失败测例）**装入本地调试会话，供网页端单步/倒退回放。
5. **进度同步**：可选将浏览器存档双向同步到本地 `user_progress.json`。

## 4. 本地 C 项目规范与通信协议

### 4.1 本地项目识别文件：`nmc.project.json`

每个第 3、4 章的玩家本地项目根目录下放置一份 `nmc.project.json`（由网页端模板生成，玩家可自由修改）：

```json
{
  "schemaVersion": 1,
  "name": "my-c-compiler",
  "track": "chapter4",
  "build": {
    "command": "gcc -Wall -Wextra -g src/*.c -o build/nmcc",
    "workingDir": ".",
    "timeoutMs": 15000
  },
  "executable": "build/nmcc",
  "watch": ["src", "include", "Makefile"]
}
```

### 4.2 玩家编译器 CLI 契约（极简且通用）

为了让任何 C 工程结构都能被游戏统一驱动，游戏对玩家编译出的可执行文件只做**最小约定**：

- **输入**：从标准输入（`stdin`）读取待翻译的源程序文本（或支持命令行传入文件路径，默认优先 `stdin`）。
- **正常输出**：向标准输出（`stdout`）打印目标产物（Token 流 / AST 文本 / BotVM 指令流 / RISC-V 汇编文本），进程退出码为 `0`。
- **错误输出**：若源程序有语法/语义错误，向标准错误（`stderr`）输出错误信息，并返回非 `0` 退出码。
- **阶段切换参数（第 4 章复用同一工程的关键）**：
  - 支持传入 `--stage <lex|parse|sema|codegen>`（例如 `nmcc --stage lex < input.c`），让玩家在**同一个不断成长的本地 C 项目**里，既能跑 4-1 词法关卡，也能跑 4-12 端到端编译关卡，互不冲突！

### 4.3 `nmc-bridge` HTTP + WebSocket 接口概览

所有 DTO 统一 `camelCase`，由共享的 TypeScript 类型定义约束：

| 类别 | 接口 / 事件 | 说明 |
|------|-----------|------|
| 状态 | `GET /api/health` | 返回 Bridge 版本、工具链状态（`gcc`/`clang`）、当前绑定项目摘要 |
| 项目 | `POST /api/project/select` | 绑定或切换本地项目目录（校验 `nmc.project.json`） |
| 项目 | `POST /api/project/init` | 在指定目录生成第 3 章或第 4 章 C 项目脚手架 |
| 构建 | `POST /api/project/build` | 触发本地编译，返回成功/失败与结构化编译日志 |
| 测试 | `POST /api/level/:id/run` | 用当前关卡默认测例跑一次（不计分，返回产物与模拟器快照） |
| 测试 | `POST /api/level/:id/submit` | 跑完该关全部测例（可先自动构建），返回 `SubmitDto`（含各测例 Diff 与失败现场） |
| 调试 | `POST /api/debug/start` / `step` / `step-back` / `continue` / `reset` / `quit` | 对某条测例（支持指定 `caseIndex`）进行单步/倒退调试 |
| 实时流 | `WS /ws` | 推送 `project.changed`、`build.log`、`test.progress`、`bridge.status` |

## 5. Web 前端与独立 Playground 架构（`web/`）

### 5.1 核心路由与页面布局

| 路由 | 页面 | 核心能力 |
|------|------|---------|
| `/` | 关卡地图与总览 | 技能树式四章导航、进度条、本地 Bridge 连接指示器、快捷进入独立 Playground |
| `/level/:id` | 关卡学习页 | 左栏：任务目标卡 + 交互式动画教学 + 分级 Hint；右栏：嵌入式 Playground（可一键最大化） |
| `/playground` | **独立 Playground 页面** | 顶栏：模式切换（`在线编辑` / `本地项目`）+ 目标关卡测例选择器（或自由沙盒）+ Watch 开关；主区：代码/项目状态 + 可视化调试画布 + 测例/控制台面板 |
| `/wiki/:topic` | 概念图鉴 | 独立可搜索的动画图解、RV32IM 指令表、C 语法与数据结构模板 |

### 5.2 统一引擎抽象（`EngineClient`）

前端 UI 组件**不直接关心**当前是 WASM 在跑还是 `nmc-bridge` 在跑，统一调用 `EngineClient` 接口：

- `OnlineWasmClient`：面向第 1~2 章与在线沙盒，直接与 Web Worker 中的 `nmc-wasm` 通信。
- `LocalBridgeClient`：面向第 3~4 章与本地项目模式，通过 `fetch` + `WebSocket` 与 `127.0.0.1:17320` 通信。
- 切换工作模式时，只需切换注入的 `EngineClient` 实现，**调试面板、寄存器动画、内存网格、Diff 视图与测例列表 100% 复用**。

### 5.3 交互式动画数据驱动原则

为了降低关卡制作成本，交互动画不针对每一关硬编码写死，而是做成**数据驱动的声明式组件**：

- **教学演示动画**：由关卡配置中的 `steps` JSON 驱动（例如高亮某行代码、动画移动某个值从 `x1` 到 `x3`、弹出简短气泡标注）。
- **实时执行动画**：直接消费模拟器返回的 `StepPayload`（`pcLine`、`regChanges`、`memChanges`、`output`）或 `BotVM` 的每步状态快照，天然支持「前进、倒退、调速播放」。

## 6. 质量守门机制（延续并扩展）

保留现有项目的两道核心质量门，并扩展第三道：

1. **门一：关卡自检（`selfcheck`）**：用每关参考解跑通全部测例（第 1~2 章用 `.s`/`.c` 参考解；第 3~4 章用参考 C 工程执行端到端验证）。
2. **门二：关卡配置一致性检查**：校验关卡元数据、初始代码、编辑器只读区域/提示行号、动画脚本引用的元素 ID 是否全部合法。
3. **门三：前后端契约测试**：校验 `nmc-wasm` / `nmc-bridge` 的 JSON 序列化与前端 `types.ts` 严格一致，防止出现字段名不匹配。
