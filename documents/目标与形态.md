## 一、这个游戏要做什么

**让一个完全外行的玩家，通过玩游戏，学会这两件事：**

1. **RISC-V 汇编**——看得懂、写得出。
2. **编译器的开发方法**——从词法分析一路做到代码生成。

并最终亲手做出：

- **目标 A（先做这个）**：用 C 语言实现一条**完整流程**——
  从 C 子集编译到 RISC-V 汇编。
- **目标 B（A 完成之后再说）**：在 A 的基础上继续加语言特性、加**分级 IR 与优化 Pass**，
  做出一个能生成**高性能目标代码**的编译器，并在一套**自制的体系结构模拟器**上运行与评分。

关于 B 的架构（**暂定，现在不实现**）：顺序单发射、带分支预测；
并且要留一个**目标架构可配置接口**，方便以后用 mod 扩展。

## 二、交付标准与手段

| 项 | 口径 |
|----|------|
| 验收标准 | **能玩**（不是"能学会"）；先把 A 做到能玩，B 之后再谈 |
| 剧情 | 要有**还说得过去**的剧情：有角色介绍、有明确的行動目标、有描写手法 |
| 教学载体 | **Wiki 是难点教学的载体**；关卡对话主要承担**剧情**，只放**必要的**教学 |
| 难代码 | 难算法的现成实现（例如支配树）**由 Wiki 直接提供**，玩家**自行选择**是否使用 |
| 玩家项目 | **一个不断长大的工程**，不是每关一个孤立小练习 |

**教学分工的意义**：对话适合给动机和钩子，不适合讲透算法。
所以"教什么"主要落在 Wiki 上，游戏负责让人**想知道**、并且**有地方练**。

## 三、大致形态（四章）

一条从"机器能懂"到"人能懂"的路，每一章换一次**玩家手里那门语言**：

| 章 | 玩家做什么 | 现在的状态 |
|----|-----------|-----------|
| 一 | 用**星之语（汇编）**让机器干活，学会读指令 | 已有 15 关 |
| 二 | 用 **C（星咒）**写程序，学会写高级语言 | 已有 14 关 |
| 三 | 做一个**"小目标"翻译器**：把一段人写的脚本翻成一台小装置能执行的指令流。目的是**第一次接触词法分析、语法分析、极其简单的指令生成** | **待重做** |
| 四 | 做一个**真编译器**：C 子集 → RISC-V 汇编 | **待重做** |

**第三章现在的想法（仅方向，细节待定）**：遗迹里有一台只有**五六条命令**的装置
（往前走、转身、取放、等待……），玩家写程序把"傀儡脚本"翻译成它能懂的指令流。
它的**难度要和"表达式计算器"同级**，不能一下让玩家做编译器。
好处是反馈可以很直观（把指令流交给装置执行，看它有没有把事办成）。

**第四章**把目标从"五六条命令的装置"升级成真机器；玩家在第三章已经走过
"切词 → 认语法 → 生成指令"这三个动作，第四章只是把它们放大。

## 四、两条已经明确的技术前提

### 4.1 完整的工具链归属（**用户澄清后的口径**）

玩家写的编译器是**本机的原生程序**，不在模拟器里跑。整条链是：

```
玩家用真 C 写编译器项目（多文件、随便多少内存）
  │  gcc 编译 → 一个本机可执行文件（大概 x86）
  ▼
在本机运行这个编译器：输入星咒源码 → 输出 RISC-V 汇编
  │  我们自研的【汇编器】
  ▼
  │  我们自研的【链接器】
  ▼
我们自研的【RISC-V 模拟器】：执行 + 评分
```

要点：
- **gcc 只负责编译玩家的编译器**（以及将来编译教学用的例程），**不用它做交叉汇编**；
- 目标代码的**汇编与链接由我们自研的工具负责**——而这恰好也是第二章、第三章
  要玩家自己做的能力（玩家自己造一遍，再用我们造的）；
- **只有"产出的目标程序"进模拟器**，玩家的编译器本身不进。

### 4.2 关于"汇编之后要不要链接"（**不一定有链接器**）

一开始是按"汇编 → 链接"两步记录的，但**链接器不一定是必要的**——
最后很可能就是**单文件**：玩家编译器吐出一段汇编，我们直接汇编成镜像给模拟器跑。

所以**不要把它当成既定形态**。真正需要确定的只有一件事：
**玩家产出的汇编，怎么变成模拟器能跑的镜像。** 两条典型形态：

| 形态 | 做什么 | 什么时候够用 |
|------|--------|-------------|
| **单文件**（可能就是终局） | 玩家的编译器把**所有东西**（含运行时支持）吐成**一段**汇编，我们直接汇编 | 玩家的编译器前后端都在一个翻译单元里产出；最简单 |
| **多模块 + 链接** | 玩家吐多个 `.s`，或需要一个**预先编好的运行时库**，于是必须"分别汇编 + 定地址" | 想教"模块化 / 链接 / 外部符号"这个层次的时候 |

**已知的技术现状**（供将来决定时参考）：现在的 `crates/riscv-assembler` 只有
"一次汇编出一个扁平镜像"的能力（`words` + `data` + **绝对地址**的符号表），
**没有目标文件、没有重定位、不能跨模块拼接**。
所以若哪天真要"多模块 + 链接"，那是一件**新工作**，不是现有能力的延伸：

- **(甲) 真做目标文件与重定位**：自定义 `.o` 格式（段 + 符号表 + 重定位表），链接器按布局回填。
  最真实、学到最多；工作量最大。
- **(丙) 折中**：只保留少数几种重定位（主要是 `jal` 与 `lui+addi` 对），链接器只做地址分配与回填。
  教学上够用，工作量可控。
- **不链接**（单文件）：以上都不需要，最简单。

## 五、待定问题清单（**不要急着决定**）

这些要么等剧情方向，要么等 A 的雏形跑起来再定：

- **4.2 选哪种形态**（单文件 / 多模块+链接；若链接，走甲还是丙）
- 第三章那台装置是什么、叫什么、几条命令、指令流有没有标签与循环
- 装置的指令集是"遗迹给的"（逆向/考古感）还是"星泠造的"（创造感）
  —— 星泠的核心动机是"让不会魔法的人也能施法"，这一点可能更支持后者
- 四章的章节名与剧情走向；主线目标是什么
- 玩家"不断长大的工程"在界面上怎么呈现（项目视图？文件树？），
  以及**玩家编译器产出的汇编是"一段"还是"多段"**
- **玩家的编译器与游戏之间用什么接口**：游戏要驱动玩家写的编译器（喂源码、收汇编），
  得约定输入输出方式（命令行参数？标准输入输出？还是约定一个函数签名？），
  以及**超时与崩溃的处理**（玩家程序可能死循环或崩掉）
- 第三章、第四章现有的 12 + 12 关内容大概率要整体重做
- 目标 B 的模拟器要做到什么程度（分支预测的建模深度、评分怎么算）
- 是否保留现有"疯狂模式"（用汇编写编译器）作为可选超难路线 / 平行宇宙

## 六、环境事实（本机实测）

写下来是为了将来"要打包什么"时有底：

- 本机有 **gcc / cc / clang / g++ / make**（都在 MSYS2 的 `mingw64` 里），
  所以"玩家用真 C 写编译器、gcc 编译它"这条流程**现在就能跑**；
- 发布游戏时需要自带一套 C 工具链（或让玩家自行安装）——**这属于打包问题，先记着**。
