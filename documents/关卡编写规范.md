# 关卡编写规范（作者必读）

> 这份文档面向**编写关卡的人（或 AI）**。读完它就能产出一个可被引擎判定的关卡。
> 架构与教学大纲见 [`总设计.md`](总设计.md)；写完请对照本文末尾的自检清单。

---

## 1. 一个关卡 = 3 个文件

| 文件 | 作用 |
|------|------|
| `compiler-content/src/cN_M.md` | 关卡页：叙事 + 编辑器配置 + 初始代码 |
| `compiler-content/src/tests/cN_M.json` | 测例与判定配置 |
| `compiler-content/solutions/cN_M.<s\|c>` | **参考解**（引擎自检用它验证测例可解） |

命名：`N` 是章号，`M` 是关号。关卡 ID 是 `"N-M"`（如 `"1-5"`），三个文件里的 ID 必须一致。
新增关卡页要登记到 `compiler-content/src/SUMMARY.md`。

---

## 2. 关卡页格式

````markdown
## 1.5 记忆晶阵

（这里写叙事与讲解，普通 Markdown。给玩家的提示要具体，别写"想想看"。）

```riscv
{
  "level": "1-5",
  "language": "asm",
  "constraints": {
    "readonlyPrefix": 2,
    "readonlySuffix": 1,
    "suggested": { "3": "lw x5, 0(x1)" }
  }
}
---
# 把 0x1000 处的数读进 x5
li x1, 0x1000
lw x5, 0(x1)
nop
ecall
```
````

### 2.1 EditorConfig 字段

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `level` | string | 必填 | 关卡 ID，如 `"1-5"` |
| `language` | `"asm"` \| `"c"` | `"asm"` | 决定编辑器高亮与后端编译路径 |
| `toolbar.run/debug/submit/load/save` | boolean | true | 按钮显隐（一般不用写） |
| `constraints.readonlyPrefix` | number | 0 | 前 N 行只读（放脚手架） |
| `constraints.readonlySuffix` | number | 0 | 后 N 行只读（放 `ecall` 收尾） |
| `constraints.hidden` | number[] | [] | 隐藏行（1-based；提交时代码原样保留） |
| `constraints.suggested` | object | {} | 行号 → 灰色提示文本 |
| `constraints.highlight` | number[] | [] | 高亮提示行 |

> `readonlyPrefix/Suffix` 用"区域"而不是行号列表：玩家在中间插行也不会破坏锁定。

## 3. 测试配置格式

```json
{
  "level": "1-5",
  "language": "asm",
  "availableOps": ["li", "lw", "ecall"],
  "forbiddenRegs": [],
  "maxInstructions": 5000,
  "goal": {
    "type": "static",
    "tests": [
      {
        "name": "读 42",
        "initial": { "regs": { "x1": 0 }, "memory": { "0x1000": 42 } },
        "expected": { "regs": { "x5": 42 } }
      }
    ]
  }
}
```

### 3.1 顶层字段

| 字段 | 必需 | 说明 |
|------|:---:|------|
| `level` | ✅ | 与关卡页一致 |
| `language` | | `"asm"`（默认）或 `"c"` |
| `availableOps` | ✅ | **允许的助记符白名单**；`[]` = 全部允许。汇编关卡：可写基础指令，也可写伪指令名（伪指令的展开部分都必须在白名单里才放行） |
| `forbiddenRegs` | ✅ | 禁止访问的寄存器，可写 `x9` 或 ABI 名 `s1`；`[]` = 全允许 |
| `maxInstructions` | ✅ | 单测例最大指令数，超限判失败（防死循环） |
| `goal` | ✅ | 见下 |

### 3.2 `goal.type = "static"`

```json
"goal": { "type": "static", "tests": [ /* 至少 1 条，建议 3 条以上 */ ] }
```

一条测例的字段（全部可选；**优先用 `call` 模式**）：

| 字段 | 说明 |
|------|------|
| `name` | 测例名（提交失败时展示给玩家，请写人话） |
| `call` | `{ "fn": "solve", "args": [3, 7] }` → **函数模式**：设好 `sp/gp`，把 args 放进 `a0..a7`，`jal` 到该函数，`a0` 作为返回值 |
| `initial.regs` | 执行前寄存器值（键 `x0`..`x31`，未列出为 0） |
| `initial.memory` | 执行前内存（键 `"0x1000"`，整数；也可写 `{"string": "abc"}` 写入 C 字符串） |
| `initial.sp` | 栈指针初值（默认 `0xF000`） |
| `input.text` | **输入字符流**（字符串）：程序从 `0xF0000004` 读到的字符，按顺序，末尾自动补「输入结束」 |
| `output.text` | **期望输出**（字符串）：程序写到 `0xF0000000` 的全部字符 |
| `expected.ret` | 期望返回值（配合 `call`） |
| `expected.regs` | 期望的寄存器终值（**只比对列出的**） |
| `expected.memory` | 期望的内存终值（**只比对列出的**；可写 `{"string": "abc"}` 或整数数组 `[1,2,3]`） |
| `expected.exitCode` | 期望退出码（`ecall` 时的 `a0`） |

**函数模式 vs 程序模式**：
- 写了 `call` → 函数模式：玩家只写一个函数，不用管初始化与收尾（**第二、三章前期用**）。
- 没写 `call` → 程序模式：从第 0 条指令开始跑，跑到 `ecall` 结束（**第一章、第三/四章后期用**）。

**输出文本的比对是"规范化"的**：两侧都按行拆分 → 去掉每行首尾空白 → 丢掉空行 → 逐行完全一致才算通过。
（也就是说缩进差异不算错，但多输出一个数就算错。）

### 3.3 `goal.type = "output"`

和 `static` 一样，但**只比对 `output.text` 与 `expected.exitCode`**，不比对寄存器。
适合"同一结果可以有多种写法"的关卡。

### 3.4 `goal.type = "scripted"`（随机/多轮判定）

```json
"goal": { "type": "scripted", "judge": "expr_check", "judgeArgs": { "rounds": 8, "maxValue": 20 } }
```

| Judge | 参数 | 作用 |
|-------|------|------|
| `expr_check` | `rounds`, `maxOperands`, `maxValue` | 随机生成 `+ - * 括号` 表达式，用 Rust 侧参考实现算答案，比对玩家输出 |
| `brackets_check` | `rounds`, `maxLen` | 随机括号串，比对玩家输出 |
| `sort_check` | `arraySize`, `maxValue`, `seed` | 随机数组 → 玩家排序 → 校验有序且为原数组的重排 |
| `compile_and_run` | `program`（星咒源码字符串）, `args`, `expectedRet` | 把**玩家输出的星之语文本**交给汇编器实际执行，比对运行结果 |

### 3.5 值类型

| 类型 | 写法 |
|------|------|
| 寄存器键 | `"x0"`..`"x31"` |
| 内存地址键 | `"0x1000"`（`0x` + 十六进制） |
| 数值 | 十进制整数，支持负数 |
| 字符串 | JSON 字符串（`\n` 等转义照常） |

## 4. 汇编关卡可用的语言

### 4.1 指令（按 `availableOps` 白名单开放）

```
add sub sll slt sltu xor srl sra or and
mul div divu rem remu
addi slti sltiu xori ori andi slli srli srai
lb lh lw lbu lhu  /  sb sh sw
beq bne blt bge bltu bgeu
jal jalr lui auipc  /  fence ebreak ecall  /  slp
```

### 4.2 伪指令（推荐逐步开放，让初学关卡更友好）

```
li la mv not neg nop j jr ret call
beqz bnez blez bgez bltz bgtz bgt ble bgtu bleu seqz snez
```

`li rd, 常量` 与 `la rd, 标签` 固定展开成 **2 条**指令（`lui` + `addi`），
白名单里必须同时有 `lui` 和 `addi`（或者干脆把 `li`/`la` 本身写进白名单）。

### 4.3 指示符

```
.text .data .org <addr> .align <n> .globl <名字>
.word .half .byte .ascii "..." .asciz "..." .space <n> .equ 名字, 值
```

表达式支持 `+ - * / % & | ^ << >> ~ ()`、字符字面量 `'A'`、标签与 `.equ` 常量。

### 4.4 系统调用（`ecall`，调用号放 `a7`）

| a7 | 作用 |
|----|------|
| 0 | 结束程序，退出码 = `a0` |
| 1 | 输出字符 `a0`（低 8 位）到显示端口 |
| 2 | 以十进制输出整数 `a0` |
| 3 | 读一个字符到 `a0`（队列空 → 0，表示输入结束） |
| 4 | 读一个十进制整数到 `a0` |
| 99 | 已消耗周期数 → `a0` |

> ⚠ **`a7` 就是 `x17`，不是 `x11`**（`x11` 是 `a1`）。这是写关卡时踩过的最惨的坑：
> 把调用号写进 `x11` 之后 `a7` 一直是 0，于是**每一个 `ecall` 都被当成"结束程序"**
> （退出码恰好等于 `a0`），现象是"程序跑得飞快、输出全空"，非常像"输出没被捕获"。
> 用数字寄存器名写参考解时务必核对：`x10..x17` = `a0..a7`。

> ⚠ **不要在参考解里把 `x1` 当普通寄存器用**：`x1` 是 `ra`，
> `jal x1, 子程序` 或 `call` 都会把它覆盖成返回地址。
> 需要"临时格子"请用 `t0`–`t6`（`x5`–`x7`、`x28`–`x31`）。

### 4.5 从输入端口读字符（第三章及以后几乎每关都要用）

```asm
li t0, 0xF0000004
lbu a0, 0(t0)       # a0 = 下一个字符；a0 == 0 表示输入结束
```

**`lw` / `lh` / `lbu` / `lb` 从输入端口读，效果完全一样：都只取走一个字符**
（有 `mmio_input_word_read_consumes_exactly_one_element` 测试钉住）。

这件事必须写下来，因为"字 = 4 字节"的直觉在这里会得出错误结论：
输入端口只映射了基地址，`addr+1..3` 落到普通内存读出 0，
所以 `lw` 的结果是"低字节是字符、其余为 0"，消费量是一个元素。

> 曾经有一次误判：某个 agent 观察到"用 `lw` 读字符会丢后面 3 个字符"，
> 于是改用 `lbu` 才"修好"。**实测（`memory.rs` 里直接数队列长度）证明两者消费量相同**，
> 真正的原因是它自己程序里的数字打印 bug。**遇到这类"某个指令行为诡异"的结论，
> 先用一段最小程序实测，别按推理下结论。**
>
> 同类误判还有一次："`ecall`（`getc`）会用 `t0` 当指针、静默破坏 `t0`"——
> 看 `sim.rs` 的 `syscall()` 就知道，系统调用**只写 `a0`**。
> 真正的原因是**调用方自己的辅助函数**把 `t0` 用掉了（见 §4.7）。
> 结论一样：把"引擎的锅"和"我自己的锅"分开，靠的是实测与读源码，不是直觉。

### 4.6 "空输出"类测例必须另外检查内存

输出文本的比对会**丢掉空行**（见 §3.2 的规范化规则）。于是：
"空输入 → 什么都不输出"这种测例，如果只写 `output.text: ""`，
一个**什么都没实现的骨架**也能通过 —— 它确实什么都没输出。

所以凡是"输入为空/结果为空"的测例，都要额外给一条 `expected.memory`
（把结果数写在 `0x2000` 这类固定位置），用来区分"算对了"和"没算"。


### 4.7 寄存器别名

`x0`=zero `x1`=ra `x2`=sp `x3`=gp `x4`=tp `x5`=t0 `x6`=t1 `x7`=t2 `x8`=s0/fp `x9`=s1
`x10`=a0 … `x17`=a7 `x18`=s2 … `x27`=s11 `x28`=t3 … `x31`=t6

**跨 `jal` 要保住的值，只能放 `s0`–`s11`。**
`t0`–`t6`、`a0`–`a7` 都是"临时格子"：你写的辅助函数（以及被调用的任何东西）
随时会用它们。把累计值放在 `t0` 里、中间调一次子程序，值是**静默**变的——
没有报错，只是结果莫名其妙地不对，排查代价极高。

> 这条在第四章被真实踩过两次：一次是"词法分析器的游标放 `t0`，
> 结果一个字节都没进缓冲区"；一次是"关键字表的指针放 `t1`，
> 被字符串比较函数冲掉，从第二个关键字起就在跟垃圾比"。两次都表现为
> "数字/标识符印错"这种**看起来像算术 bug** 的形态。
> 而 `crates/riscv-simulator` 的系统调用**不碰任何 `t` 寄存器**（只写 `a0`）——
> 别把锅扣到引擎头上。

本章最推荐的写法：

```asm
# 一进函数就把要跨调用保留的东西压栈（或用 s 系列）
addi sp, sp, -8
sw   s0, 4(sp)
...
lw   s0, 4(sp)
addi sp, sp, 8
ret
```

### 4.8 数据段与对齐（用 `.data` 的关卡必读）

**`.word` / `.half` 不会自动对齐。** 例如：

```asm
.data
msg:  .asciz "abc"      # 占 4 字节（含结尾的 0），下一条数据从 +4 开始
x:    .word 0           # 正好对齐，没事
msg2: .asciz "abcd"     # 占 5 字节
y:    .word 0           # 落在 4 字节边界之外！
```

`y` 的地址不是 4 的倍数，`lw`/`sw` 读它会被模拟器直接判**未对齐访问**（运行时错误，
不是警告）。所以"字符串后面接一个字"时，**要显式写 `.align 4`**：

```asm
msg2: .asciz "abcd"
      .align 4
y:    .word 0
```

## 5. 星咒（C）关卡

`language: "c"`。玩家写的是 C 子集（见总设计 §4）。要点：

- 函数模式关卡：玩家只写一个函数，例如
  ```c
  int solve(int a, int b) {
      return a + b;
  }
  ```
  测例写 `"call": { "fn": "solve", "args": [3, 7] }` + `"expected": { "ret": 10 }`。
- 程序模式关卡：玩家写 `int main()` 风格的代码，用 `putchar` / `getchar` / `print_int` / `print_str` 交互；
  测例写 `input.text` 与 `output.text`。
- 内建函数（无需声明即可用）：`putchar(c)` `getchar()` `print_int(n)` `print_str(char* s)` `exit(code)`。

## 6. 叙事写作要求

1. **每关都要有一个"现在必须解决的麻烦"**，不要写纯教程。
2. 名词统一：计算机 = 魔导核心，处理器 = 魔导引擎，存储器 = 记忆晶阵，
   汇编 = 星之语，指令 = 星之印，高级语言 = 高阶语，周期消耗 = 魔力消耗。
   但**寄存器、指令、内存、函数**这些系统术语照常用真实说法。
3. 角色：**星泠**（冷静、技术型，负责讲解与推理）、**岩舟**（实干、爱自嘲，负责提问与推动）、
   **伊塔尔**（古代魔法师，只通过留下的记录出场）。
4. 讲解要"先给画面再给术语"，一次只引入一个新概念。
5. 每关结尾给一句**下一步的钩子**。
