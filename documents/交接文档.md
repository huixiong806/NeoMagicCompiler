## 1. 关键环境事实（踩过的坑，别再踩）

| 事项 | 结论 |
|------|------|
| 工具链 | cargo 1.94 / rustc 1.94 / node 24 / mdbook 0.5.3 / git 2.35，全部可用 |
| Windows 编码坑 | **绝对不要**用 `Set-Content` / `Out-File` / `Get-Content\|Set-Content` 写含中文的源文件（会按 GBK 解释导致乱码毁文件）。只用 `write` / `edit` 工具改文件。曾经因此毁过 `lib.rs` 与一批 `solutions/*.s`（后者不可逆）。 |
| ⚠ 重要更正 | PowerShell 控制台**显示**中文乱码（GBK 解码）**不代表文件坏了**。判断编码要看 `read` 工具或按 UTF-8 解码。曾经据此误判过一批好文件。 |
| 离线构建 | 根目录 `.cargo/config.toml` 设了 `[net] offline = true`。依赖全在本地缓存。**不设它会出现"看起来像死锁"的现象**：多个 cargo 争 crates.io 索引/包缓存锁，一堆 cargo 进程、零个 rustc。已踩过一次（22 个 cargo 全卡住）。 |
| 并发构建 | 多个子代理同时 `cargo test` 会抢 `target/` 锁（`Blocking waiting for file lock`）。对策：等 30 秒重试；或给子代理指定独立 `CARGO_TARGET_DIR`（但**记得事后删掉**，一次留下了 269 MB）。 |
| 子代理卫生 | 关卡作者会留**调试残件**：探针关卡 `c0_0.md`/`c9_9.md`、`ztmp_probe/`、独立 target 目录。`.gitignore` 已挡住一部分，但**每次 commit 前都要 `git status --short` 看一眼**（已经被误提交过两次）。 |
| PowerShell | 输出里含中文时用 `Select-String` 过滤，避免刷屏；`echo` 长输出会截断并存到 spill 文件 |
| 测试输出刷屏 | 别把大字符串直接 `assert_eq!`，会打出几 MB。要断言长字符串先比长度或取前缀 |
| Cargo workspace | 根 `Cargo.toml` 的 `members`，新 crate 必须登记 |
| 提交 | 用 `write` 把提交信息写进临时 UTF-8 文件，再 `git commit -F <file>`。**不要**用 PowerShell here-string（`<<'EOF'` 在 pwsh 里不合法），也不要在命令行里内联多行中文。 |

## 2. 架构（已冻结，改主意前请三思）

```
compiler-content/frontend (TS + Lit + Vite)   ← 编辑器 / 调试面板 / 控制台
        │ Tauri IPC (invoke, 15 条命令, 全 camelCase)
app/src-tauri
        ├── lib.rs   ← 薄转发层（只做参数转发与错误包装）
        ├── api.rs   ← 逻辑层：不依赖 Tauri，可被 cargo test 直接覆盖
        └── dto.rs   ← 接口定义：与 frontend/src/core/types.ts 一一对应
        │ Rust 函数调用
crates/neomagic-core                           ← 关卡加载/运行器/判定器/Judge/存档/自检
        ├── crates/starlang                    ← 星咒（C 子集）编译器 → 星之语源码
        ├── crates/riscv-assembler             ← 星之语汇编器（文本 → 机器码）
        └── crates/riscv-simulator             ← RV32IM 模拟器
```

**没有独立进程**：Assembler 与 Judge 都收进进程内（纯函数）。

**分层纪律（很重要，别退化）**：业务逻辑**不要**写进 `#[tauri::command]` 里。
命令的入参是 `State<'_, T>`，测试里造不出来，一旦逻辑写进去，整条 IPC 链路就只能靠手点游戏验证。
现在的分工让 `cargo test -p neomagiccompiler`（10 条集成测试）能覆盖：
关卡列表 / 参考解防回归 / 错误代码可读报错 / 单步-倒退-继续-重置 / 存档往返 / 未知关卡不 panic。

### 关卡内容如何进二进制

`crates/neomagic-core/build.rs` 扫描 `compiler-content/{src,solutions}` 生成 `embedded_manifest.rs`；
开了 `embedded-content` 特性（桌面壳开着）就编进二进制，装好的游戏不依赖仓库目录。
`LevelStore::prefer_repo_or_embedded()`：**开发时优先读磁盘**（改完关卡刷新就能看到），
磁盘上没有才用嵌入内容。
两个副产品：
- `NMC_SELFCHECK=3-4,3-5 cargo test -p neomagic-core selfcheck_only` —— 只查指定关卡，
  作者并行写内容时互不打扰；
- `embedded_content_matches_the_repository` 测试 —— 嵌入内容必须与仓库一致。

### crates/riscv-simulator（✅ 已完成）

文件：`src/lib.rs`(公共 API 导出) `src/config.rs` `src/decode.rs` `src/sim.rs`(+ `src/sim/tests.rs`) `src/history.rs` `src/memory.rs`

- **RV32IM 全指令集** + `fence`/`ebreak`/`ecall`/`slp`（原创等待指令，funct12 承载周期数）。
- **内存**：RAM 64 KiB(`0x0`–`0xFFFF`)，MMIO 区 `>= 0xF000_0000` 放行；
  `0xF0000000` 显示端口(写) / `0xF0000004` 输入端口(读 FIFO) / `0xF0000008` 魔力计(只读=已耗周期)。
- **系统调用**（`a7`）：0/5=EXIT（**唯一会暂停程序的 ecall**）、1=PUTC、2=PUTC_INT、3=GETC、4=GETINT、99=TIME。
- **暂停条件** `PauseOn`：ebreak/ecall/mmio_read_empty/mmio_write/error/limit/sleep。
- **历史与倒退**：`step_back(n)` / `rewind_to(tick)`，环形缓冲，`history_capacity`。
- **核心语义（务必记住）**：
  - 普通 `ecall`（putc 等）**不暂停**；只有 `SYS_EXIT` 触发 `PauseReason::Exit{code}`。
  - `reset()` **保留** MMIO 输入队列与输出记录（输入属于"外部世界"）。
  - 错误（段错误/未对齐/未知指令/白名单/禁止寄存器）一定停下，`PauseReason::Error`。
  - `slp n` 消耗 n+1 个 tick（自身 1 + 等待 n）。
- 测试：`cargo test -p riscv-simulator`（约 49 个）。

### crates/riscv-assembler（✅ 已完成）

### 修 bug 的工作流（试玩阶段照着走，省 token）

1. **听一个具体现象**（"3-5 提交后报错但我觉得对""点倒退没反应"），不要一开始就大面积读代码。
2. **先把现象变成可复现的证据**，优先用现成工具而不是自己翻源码：
   - `NMC_SELFCHECK="3-5"` + `cargo test -p neomagic-core selfcheck_only` → 这一关现在绿不绿；
   - 加 `NMC_SELFCHECK_VERBOSE=1` 跑 `selfcheck_verbose` → **逐条测例**打印"输入/期望/实际"；
   - 若是引擎行为可疑（某个指令、MMIO、暂停条件），**写一个最小程序实测**
     （直接 `assemble` + `Simulator` 跑几行），不要靠推理下结论 ——
     本项目已经有两条"像引擎 bug"的断言被实测推翻过。
3. **把证据与复现步骤写成一段独立简报，派给子代理去修**（模板见 §6）。
   主上下文只保留判断与验证，不要自己一头扎进汇编文件里 —— 这一轮我在这上面烧掉了大量上下文。
4. **修完必须验证**：相关关卡自检绿 + `cargo test --workspace` 绿，然后提交。
5. **把结论写进本文件**（进度日志 + 如果是通用教训，写进 `关卡编写规范.md`）。

### 进度门禁的设计决定（用户拍板，2026-02）

用户试玩后提出："第一关没提交就可以进第二关，这不符合游戏逻辑。"
追问后确定为：

- **方案 A：单一存档**（不做登录/密码；多档案是过度设计，因为单机没有服务端，
  本地存密码等于没有安全性）。**但数据结构要预留扩展成 B（多份本地档案）的余地** ——
  不要把关卡/存档路径写死得到处都是。
- **通过才解锁**（不是"提交过就解锁"）。理由（用户原话）：
  "我们现在关卡数很少，每一关信息量巨大，理解不了直接开下一关肯定还是理解不了。"
- **不能提前看下一关**：不只是禁用按钮，还要拦住**侧边栏导航**与**直接打开 URL**
  （否则改个地址就绕过去了）。被拦住时给一句符合世界观的说明，
  并把玩家带回"当前该在的那一关"。
- **已通过的关卡可以随时重进重打**（复习用），不要"通关即锁"。

**⚠ 但用户随后收紧了范围（原话）**：

> "我建议不要花太多时间拦一个非要进到下一关的用户，只要让正常用的用户别轻易进到下一关就行。
> 我们是单机游戏，不难为玩家，只要让玩家别不小心走到了不推荐的路线即可，故意的不拦。"

所以最终口径是：

| 做法 | 要不要 |
|------|-------|
| 侧边栏把未解锁关卡标出来、点它不跳转 | **要做**（这是"不让人不小心走错路"的主要手段） |
| 解锁判定放领域层 + 单测（含"手改存档不能跳过解锁"） | **要做**（数据正确性，与拦不拦玩家无关） |
| 页面级强制拦截 / 重定向回该在的关卡 | **不做**（我原先自己加戏了） |
| 打开未解锁 URL 时阻挡、禁用编辑器、弹窗 | **不做**；最多给一句友好提示，也可以完全不管 |

**这条口径是个通用教训**：单机游戏的门禁目的是"**引导**"，不是"**防止作弊**"。
以后遇到类似的"要不要防住用户"的问题，先问一句是引导还是防作弊 —— 单机一律按引导做。
