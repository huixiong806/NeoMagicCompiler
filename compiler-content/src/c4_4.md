## 4.4 先乘后加：谁先动手

第二块石板比第一块长得多，刻痕里第一次出现了括号。

```
1+2*3
```

岩舟看了一眼就动手："一加二等于三，三乘三等于九。"他在石板边缘的那个小孔里塞进一颗感应石，孔没亮。

"九不对。"星泠说。

"不对？"

星泠没直接回答。她指着那一行刻痕："你刚才干了什么？"

"从左往右念了一遍。"

"对。这就是问题所在。"她从怀里取出第一块石板的拓片，摊在旁边，"第一块石板上只有 `+` 和 `-`，从左往右确实没错——那时候**所有运算符面子一样大**。可是现在来了 `*`。"

她在灰上画了两个方向：

```text
   左往右：(1+2)*3 = 9
   先乘后加：1+(2*3) = 7
```

"同一行刻痕，两种念法。**刻痕自己没写哪一种是对的**——是念它的人的脑子里带着一条规矩。这条规矩不写下来，机器就不知道。"

岩舟把感应石抠出来，重新想了想。"所以我们要把这条规矩也刻进程序里。"

"而且要刻得**和括号握手**。"星泠说，"看第二行：`(1+2)*3`。这一次是**刻痕自己**说了'先算括号里'——括号一出现，前面那条规矩就得让路。"

她把手按在石板上：

"上一关我们对付的是'所有运算符一样大'。这一关要处理的是**优先级**，而且必须把括号一起处理好。做法只有一条路，而且你已经会了——"

**递归下降**。写法是三层函数，一层管一档优先级：

```text
parse_expr   （管 + -）：先要一个 term，然后只要还看到 + 或 -，就再要一个 term
parse_term   （管 * /）：先要一个 factor，然后只要还看到 * 或 /，就再要一个 factor
parse_factor （管'最小的东西'）：要么是一个数字，要么是 ( 一整个 expr )
```

"读法就是它字面的意思：**一个 expr 是一串 term 用 `+`/`-` 串起来**。所以 `parse_expr` 只管找到下一个 `+` 或 `-`，中间那些乘除它一概不管——乘除的事交给 `parse_term`，而 `parse_term` 里 `*` 和 `/` 又会自动被它收进去。"

岩舟把 `1+2*3` 在灰上走了一遍，终于看明白那个关键点：

```text
parse_expr
  parse_term → 1        （term 看到的是 '+'，不是 '*'，所以它收手了）
  看到 '+' → 再要一个 term
  parse_term
      parse_factor → 2
      看到 '*' → 再要一个 factor → 3
      ⇒ term 把 2*3 整个吃掉了
```

"**加号那一层根本不知道乘号的存在**——它只看得到 `1` 和 `2*3` 两个整体。于是 7 就自己出来了，不是我们算出来的，是**结构**逼出来的。"

"括号呢？"

"括号是最漂亮的一层：`parse_factor` 看到 `(`，就去要一个**完整的 expr**，要完再吃掉 `)`。也就是说——**括号里的世界，是从最高层重新开始的**。所以 `(1+2)*3` 里那个 `+` 有资格比外面的 `*` 先算。"

至于输出，还是上一关那套后缀：解析的路上顺手把 `NUM:值` 和 `OP:符号` 一个个吐出来，**括号只是路标，不输出**。数字被完整吃掉的那一刻吐 `NUM:`，运算符那层收工时吐 `OP:`。

"这一关的难点只有一个，"星泠最后说，"`*` 和 `/` 要多出来一层。上一关那两层骨架（expr→term）你直接搬过来，只要在 term 里多循环一次乘除就行。"

她压低声音补了一句："还有一件事——石板底下那行刻痕，比上面这两行深得多。它刻的**不是一段表达式，是一整个小片段**。等我拓完再说。"

---

**本关任务**：读入一行只有非负整数和 `+ - * / ( )` 的表达式，输出它的**中缀 → 后缀（RPN）**结果，一个 token 一行。

### 输入与输出格式（4.4）

**输入**：一行表达式，只含 `0-9`、`+ - * /`、`(`、`)`；数字是不带符号的非负整数（`7`、`12`、`345`）。例子：`1+2*3`。行尾有 `\n`（值 10）。

程序按 4-1 起的约定读输入：从 `0xF0000004` **按字节**读一个字符，读到 `0` 表示输入结束。

> ⚠️ 本关的输入是**字符**，不是数字：从 `0xF0000004` 读一次只取走**一个**字符，
> 且必须以 `0` 作为"输入结束"的判据（读到 `0` 就收工）。
> （`lbu` 与 `lw` 在这个端口上的消费量是一样的，都是一次一个字符；
> `lw` 读到的后三个字节是 0。用哪个都行，但**别指望一次读回 4 个字符**。）
> 空字符（空格、`\n`、`\r`）在读进去之后顺手跳过即可。

**输出**：每个 token 一行，形如 `KIND:值`：

| token | 写法 | 例子 |
|-------|------|------|
| 数字 | `NUM:十进制值` | 输入里的 `12` → 输出 `NUM:12` |
| 运算符 | `OP:符号` | 输入里的 `*` → 输出 `OP:*` |
| 括号 | **不输出** | `(` `)` 只是路标 |

`1+2*3` 的完整输出是五行：

```text
NUM:1
NUM:2
NUM:3
OP:*
OP:+
```

即 `1 2 3 * +`。再看两个例子：

| 输入 | 输出（一行一个 token） |
|------|------------------------|
| `(1+2)*3` | `NUM:1` `NUM:2` `OP:+` `NUM:3` `OP:*` |
| `1+2` | `NUM:1` `NUM:2` `OP:+` |

注意第二条：括号**没有**出现在输出里，但它改变了 `OP:+` 和 `OP:*` 的先后——**括号的功劳藏在顺序里**。

判定时输出按行比对（去掉每行首尾空白、丢掉空行），所以空行和缩进不影响，但**多一个 token 就是错**。

**提示**：解析的写法只有一条铁律：**`t0` 就是"现在手上的字符"**。谁读到的字符就归谁看——某一层读到不属于自己的运算符，就把它**留在 `t0` 里直接返回**，上一层拿到的正好是它要的"向前看"那一格；上一层该"往前挪一格"时再调读字符函数即可。

> ⚠️ 别另外搞一个"回退槽"把同一个字符存第二份（读到看不上的字符就往槽里塞，让上一层先从槽里取）。听上去很聪明，其实是**把同一个字符记了两遍**：上一层接下来说的"往前挪一格"会又读回这个字符，位置一步没动，循环永远出不去。症状是程序不结束、输出疯狂刷屏（`3+5` 就能触发）。

> ⚠️ 还有一个同类的坑，藏在 `parse_term` 的栈帧里：`parse_expr` 把自己的运算符放在 `t3` 上，托付给 `parse_term` 一起跨过子调用；所以 `parse_term` 的栈帧要给**两样东西两个格子**——"调用者的 `t3`"和"本层自己的运算符"。两样挤进同一格，本层一吃到 `*` 就把调用者的 `+` 覆盖了，上一层随后印出来的就是 `*`（症状：`1+2*3` 输出 `OP:*` `OP:*`，最后一个 `OP:+` 不见了）。
